# 🤖 Auto-Doc-Tool Agent

**基于多智能体协同与 AST 解析的自动化实验报告生成系统**

Auto-Doc-Tool 是一个面向开发者的文档自动化工具。系统通过接入本地化部署的大语言模型（如 Ollama + Qwen2.5:7b），结合代码容错解析（Tree-sitter）与运行日志分析，将工程代码提取为结构化数据，并填充至自定义 Word 模板中，协助自动生成符合通用学术与工程规范的 `.docx` 实验报告。

---

## 一、 系统架构图 (System Architecture)

系统采用模块化多智能体架构，实现了从数据上传、大模型推演到文档渲染的完整工作流：

```text
┌─────────────────────────────────────────────────────────┐
│               1. 交互与通信层 (Gradio Web UI)             │
│  (支持异步处理与 SSE 状态推送，缓解长耗时推理导致的断连)     │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│               2. 预处理与解析层 (Tree-sitter AST)         │
│  (支持语法容错解析，提取 import/模型加载/核心类/主入口)      │
└─┬────────────────────────┬────────────────────────────┬─┘
  ▼                        ▼                            ▼
┌─────────┐            ┌─────────┐                  ┌─────────┐
│ 宏观大脑 │            │ 微观探针 │                  │ QA 智能体│
│ (Macro) │            │ (Micro) │                  │ (QA)    │
│架构与拓扑│            │AST 级直喂│                  │运行日志提取│
└─────────┘            └─────────┘                  └─────────┘
  │                        │                            │
  └────────────────────────┼────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│               3. 渲染与输出层 (Word Rendering)            │
│ (基于 docxtpl 引擎，实现内容生成与排版格式的物理隔离)        │
└─────────────────────────────────────────────────────────┘

```

**架构模块说明：**

* **交互与通信层**：前端基于 Gradio 构建，采用生成器持续推送状态，保障大模型长时间推理时的连接稳定性。
* **预处理与解析层**：在模型介入前，利用 Tree-sitter 将代码转化为 AST，并降维提取为结构化拓扑，降低模型的理解成本。
* **核心大脑层 (Three-Brain Matrix)**：
* **宏观大脑 (Macro)**：基于全局图谱上下文，生成系统整体的架构描述。
* **微观探针 (Micro)**：采用切片直喂策略，对局部代码模块的具体逻辑进行提取。
* **QA 智能体 (QA)**：解析现场运行日志，提取包含真实参数的操作步骤。


* **渲染与输出层**：排版工作交由 `.docx` 模板引擎处理，Python 端仅负责文本注入，保障最终文档格式的稳定性。

## 二、 核心技术机制 (Technical Features)

本项目在常规 LLM 调用的基础上，引入了以下控制机制以提升输出质量：

* **AST 序列化与极限容错**：废弃原生的 `ast` 模块，引入 `Tree-sitter` 引擎。即使输入代码存在局部语法缺失，也能强行提取完好的代码片段，并将其转换为大模型易于解析的 XML 结构图谱。
* **图谱化全局黑板 (Graph-Context Blackboard)**：在多智能体之间建立共享内存池。微观组件提取的事实会被打上“底层环境”、“核心逻辑”等拓扑标签再写入黑板，为宏观大脑提供具有上下游依赖关系的推演上下文。
* **Actor-Critic 审查隔离**：为提升文本的专业度，系统在代码逻辑提取（Actor）和文本润色（Critic）之间采用物理隔离的双模型流，结合 Few-Shot 提示词，有效过滤模型生成的口语化表述和冗余评价词，输出客观的被动语态陈述。
* **语义路由记忆库 (Semantic Memory Routing)**：内置自反思机制，系统会在运行结束后提取具有指导意义的“写作元法则”。通过 TF-IDF 或基础关键词路由，系统在下一次运行时只调取与当前工程语义（如视觉、硬件控制）相关的记忆，避免上下文污染。

## 三、 系统表现与限制 (Performance & Limitations)

* **代码解析准确度**：通过 AST 直喂，系统在描述函数名、引用库和关键变量时，能有效减少模型的虚构和“幻觉”现象。
* **行文规范性**：经过 Critic 审查后，生成的文本主观修饰词（如“完美实现”、“极大提高”）显著减少，行文风格趋向工程客观描述。
* **格式确定性**：成功隔离了 LLM 常规的 Markdown 标记输出，Word 模板中的图片占位和代码缩进能够被严格保留。
* **当前局限**：系统目前依赖本地单机大模型（7B级别），对于超大规模项目的深层隐式逻辑关联推演，仍存在一定的理解瓶颈，适合作为初稿生成工具使用。

## 四、 部署与运行指南 (Deployment)

### 1. 环境依赖

建议使用 Python 3.9+ 环境。在本地运行前，需安装以下依赖（注意部分库需严格锁定版本）：

```bash
pip install "tree-sitter==0.21.3" "tree-sitter-python==0.21.0"
pip install "crewai==0.41.1" "langchain>=0.2.0,<0.3.0"
pip install gradio docxtpl python-docx requests

```

### 2. 模型服务端配置 (Ollama)

系统默认请求本地 `127.0.0.1:11434` 端口的 Qwen2.5:7b 模型。如采用算力端分离部署：

1. 在服务器启动 Ollama 并允许外部访问：
```bash
export OLLAMA_HOST=0.0.0.0
nohup ollama serve > ollama.log 2>&1 &

```


2. 使用内网穿透工具（如 Ngrok）暴露 API：
```bash
nohup ngrok http --domain=your-domain.ngrok-free.app 11434 > ngrok.log 2>&1 &

```


3. 将 `auto_tool.py` 源码中的 API 请求地址统一替换为上述域名。

### 3. 模板与运行

1. 请确保项目根目录下存在所需的模板文件（如 `template_complex.docx`）。
2. 确保 Ollama 服务正常运行后，执行主程序：
```bash
python web_ui.py
```
